Collection

Collection is where operational truth enters Watchpost. The design gives equal weight to provenance and failure behaviour—not just the happy-path numeric value.

First-party coverage

The initial programme calls for host CPU, memory, disks, load, uptime, and process observations, followed by HTTP, TCP, and TLS checks including latency and certificate expiry. Broader integrations should use the same versioned ingestion contract.

Observation envelope

Every accepted observation should be attributable and bounded. The proposed envelope includes:

  • stable target and collector identity;
  • observation time and ingestion time;
  • signal name, type, value, and unit;
  • quality and freshness state;
  • bounded labels and optional structured evidence;
  • collector contract version and sequence/replay information.

Push and pull

Watchpost should support both. Pull checks are simple for reachable targets; authenticated push supports isolated or ephemeral environments. Neither mode escapes payload limits, identity, rate control, replay defence, or backpressure.

Cardinality and volume

Labels, logs, process lists, and per-request dimensions can exhaust memory and disk long before raw sample count does. Watchpost will expose budgets and rejected or dropped data instead of hiding them as implementation detail.

Important invariant

A collector failure must be observable as collector failure. It must not manufacture healthy target data or silently preserve an old value as current.

Collector isolation

Third-party integrations will use an explicit protocol or process boundary rather than executing arbitrary plugins inside the primary server. Exact extension mechanics remain to be designed.
