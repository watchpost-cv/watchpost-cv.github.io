Collection

Collection is where operational truth enters Watchpost. Every observation has a post identity, source, event time, ingestion time, quality, and bounded payload.

Collector protocol v1

WP02R defines atomic batches of 1–128 samples, one post and collector identity, contiguous sequence numbers, bounded clocks and labels, explicit quality, and an acknowledgement through the last accepted sequence. Unknown protocol versions and partial batches fail closed.

Immediate checks

The Run a check view performs an immediate HTTP, ICMP, TCP, DNS, or TLS check. These are useful for enrollment and diagnosis.

HTTP  https://example.com/health
TCP   database.internal:5432
DNS   api.internal.example
TLS   example.com:443  server name: example.com

A failed check reports failure rather than manufacturing a healthy value.

Monitor a Linux machine

Open Add a machine or device, give the post a durable ID and name, and record its IP address or hostname. The address is useful inventory and can be used by active checks; it is not an inbound agent endpoint. Choose Host and optionally add starter CPU, memory, and disk rules. Watchpost continues directly to pairing.

  1. Copy the compiled watchpost binary to the monitored Linux machine. If Watchpost and the post are the same machine, use the binary you already started.
  2. On the pairing page, enter a Watchpost URL the post can reach. 127.0.0.1 only works when both processes are on that same machine.
  3. Generate and run the commands on the post:
./watchpost collector pair \
  --server https://watchpost.example.com \
  --token ONE_USE_TOKEN
./watchpost collector install
./watchpost collector status
./watchpost collector logs

The token expires after ten minutes and works once. It is exchanged for a post-scoped credential stored in a private local configuration. Installation copies the binary to a stable path and enables a hardened per-user systemd service. Use root with --system only for a deliberate machine-wide service.

The collector reads local Linux resource interfaces and sends signed batches outbound to Watchpost. It does not listen on a management port. A per-post web frontend is intentionally not required: it would multiply the configuration surface and expose another network service. A future opt-in local diagnostics view may be useful, but central policy and identity should remain at Watchpost.

The pairing page waits for the first accepted batch, confirms collector health, and links to Resource survey and Rules. Before transmission, each batch is written atomically to a private queue. Disconnection retains up to 256 batches or 8 MiB, retries back off, and only acknowledged data is removed.

Edit, archive, or delete a post

Use Posts → Edit to change the display name, address, owner, maintenance state, or archive state. The durable post ID cannot be changed because observations, rules, and evidence are bound to it.

Archiving hides a post from ordinary work while preserving its history. Permanent deletion is different: an administrator must type the exact post ID, and Watchpost removes the post, collector credentials, samples, rules, alerts, logs, device profiles, and post-scoped investigation history. Use deletion only when that evidence is genuinely unwanted.

Submit one observation

curl --request POST http://watchpost-host:8080/api/v1/observations \
  --header "Authorization: Bearer $COLLECTOR_SECRET" \
  --header "Content-Type: application/json" \
  --data '{
    "version": 1,
    "post_id": "laptop",
    "collector_id": "laptop-host-agent",
    "observed_at": "2026-08-28T12:00:00Z",
    "sequence": 1,
    "signal": "cpu.percent",
    "value": 37.2,
    "unit": "percent",
    "quality": "good",
    "labels": {}
  }'

Collector health

The Collectors view distinguishes never connected, healthy, stale, offline, skewed, rejected, partial, and revoked. These states come from durable receipt, observation, clock, rejection, and quality facts; an empty history is never called healthy.

Survey every post

Resource survey draws one-hour sparklines and latest CPU, memory, and disk values across all enrolled posts. Missing cards say “No samples” instead of presenting missing data as zero. One bounded API query supplies the whole screen.

Read-only SNMPv3

The SNMP setup guide uses authPriv with SHA-256 authentication and AES privacy. Enter the address and credentials, select a bounded device kind, add no more than 64 named OIDs, then test the connection.

name: uptime
oid:  .1.3.6.1.2.1.1.3.0
unit: ticks

Initial coverage prioritizes network devices, UPS/PDU equipment, environmental sensors, and storage appliances.

Logs and changes

Use Evidence to add or search bounded logs. Change records capture deployments, configuration updates, maintenance, and other operational context.

Future devices

Cameras, arbitrary consumer IoT, PLC writes, and building-control commands remain future exploration areas. Camera work should begin with availability and health rather than video ingestion. PLC writes and building-control commands require a separate threat model and must never be presented as safety control.

Collector invariant

Failure, lateness, and partial data remain visible. Old data is not silently presented as current, and missing observations are not converted to zero.
