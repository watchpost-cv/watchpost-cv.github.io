Data and retention

Operational history is useful only when its meaning survives storage. Watchpost begins with an explicit SQLite-first boundary and visible limits.

SQLite foundation

The proposed first database owns configuration, accounts, sessions, inventory, rules, alert state, incidents, audit, jobs, and modest telemetry. Ordered migrations are part of the application contract, with recovery tests for interrupted upgrades.

Telemetry evolution

High-volume time series may eventually move to append-oriented segments or a dedicated optional backend. That evolution should preserve Watchpost’s signal identity, units, quality, freshness, retention, and query contracts rather than infecting the product model with one storage engine.

Retention policy

Raw samples, aggregates, logs, events, incidents, audit, and agent conversations have different value and risk. Retention will be configured per class with disk budgets, compaction visibility, and safe deletion semantics.

Backpressure and loss

When Watchpost cannot keep up, it must expose queue depth, rejected payloads, dropped observations, sampling, and stale state. Silent loss is not acceptable monitoring behaviour.

Export and portability

Operators should be able to export inventory, rules, incident evidence, and selected telemetry in documented formats. Configuration and incident history must not become hostage to the UI.

Backup and restore

The project will publish a consistent backup boundary, restore validation, and upgrade rollback procedure before a stable release. Database presence alone is not proof that a backup is complete.
