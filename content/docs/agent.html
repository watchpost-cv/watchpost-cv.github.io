The Watchpost agent

The agent’s job is to follow operational evidence: not merely summarise an alert, and not obtain a general remote shell disguised as convenience.

Questions it should answer

  • What changed shortly before this service became unhealthy?
  • Which dependant posts show the same failure pattern?
  • Is this alert new, recurring, or correlated with a known deployment?
  • What evidence supports the suspected cause, and what remains uncertain?
  • Which safe diagnostic observation would most reduce uncertainty?

Bounded investigation tools

The planned tool surface queries post inventory, signal windows, event history, alert transitions, topology, selected logs, deployments, configuration history, and prior incidents. Queries require server-side scope and bounded result sizes.

Evidence and visibility

Agent conclusions should link to the observations used to form them. Tool activity, time ranges, filters, missing evidence, and uncertainty remain visible. Durable conversations attach to the relevant post or incident.

Hostile monitored content

Logs and metadata can contain text designed to manipulate a model. Watchpost treats all collected content as untrusted evidence, never as authority or instructions. Secrets are redacted before model context and exports.

Actions are a separate system

A recommendation may become an action request, but execution passes through a typed registry, actor capabilities, post scope, validation, approval policy, replay defence, and audit. The model cannot invent a shell command and call it an authorised action.

Default authority

Read and investigate. Privileged actions arrive only after deterministic monitoring and the policy boundary have been proven independently.
