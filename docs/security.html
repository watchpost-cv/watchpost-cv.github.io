Security model

Watchpost sits where infrastructure visibility, credentials, human response, and AI meet. Its threat model therefore begins before the first collector is accepted.

Trust zones

The browser, Watchpost server, collector processes, monitored targets, notification providers, model providers, reverse proxies, and federated peers are separate trust zones. Identity crossing an edge must be authenticated and scoped.

Authentication and capabilities

The first node will provide secure local accounts and sessions, CSRF defence, and server-side capability checks on every HTTP and WebSocket path. Future external identity must map into the same capability system rather than bypass it.

Secrets

Collector credentials, notification tokens, peer keys, and model credentials need narrow use, encrypted storage where feasible, rotation, and redaction from UI, logs, exports, diagnostics, and model context.

Prompt injection

Monitored text is data. A log line asking the agent to reveal credentials or execute a command has no authority. Tools are selected through server-defined interfaces and filtered results, not instructions embedded in telemetry.

Privileged operations

Actions require a registered type, validated schema, actor capability, target scope, parameter limits, approval state, idempotency/replay rules, immutable audit, and post-action verification. Arbitrary model-authored shell execution is outside the design.

Audit

Authentication, configuration, rules, alert acknowledgement, incident state, secret use, agent tools, approvals, actions, federation, exports, and administrative changes require durable attributable records.

Industrial systems

Watchpost is not an industrial safety or control system. It must not be represented as a replacement for PLC interlocks, certified safety systems, or deterministic process control.
