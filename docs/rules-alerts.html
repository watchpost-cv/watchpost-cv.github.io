Rules and alerts

Rules turn observations into deterministic operational state. Language models may help explain or draft rules, but they do not evaluate whether an alert is firing.

Rule semantics

A useful rule needs more than a threshold. The planned model includes evaluation windows, duration, hysteresis, missing-data policy, dependency suppression, maintenance windows, and explicit recovery conditions.

# Conceptual rule — syntax not final
when: http.latency.p95 > 500ms
for: 5m
recover_below: 350ms
missing: unknown
severity: warning

Lifecycle

The initial state model will distinguish pending, firing, acknowledged, resolved, and suppressed states. Acknowledgement records operator awareness; it does not change the measured condition or erase history.

Noise control

  • Deduplicate repeated evaluation of the same active condition.
  • Use duration and hysteresis to avoid rapid state flapping.
  • Suppress dependants when an upstream post is known unavailable.
  • Apply bounded notification retries and per-route rate limits.
  • Make maintenance state visible rather than dropping evidence.

Reproducibility

Rule evaluation should be replayable against recorded observations and a virtual clock. Given the same rule version and evidence, replay should produce the same transitions as live evaluation.

Notifications

Email and generic webhooks are the proposed initial routes. Routing belongs to deterministic policy: severity, ownership, schedule, labels, escalation, and delivery state remain inspectable without a model.
